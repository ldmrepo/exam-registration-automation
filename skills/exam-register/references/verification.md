# 원본·초안·저장 결과 검증

추출 담당은 원본 해석을, 편집 담당은 실제 등록 결과를, 마스터는 전체 항목과 인계 증거를 책임진다. 체크리스트가 존재한다는 사실만으로 통과시키지 않는다.

## 문항별 증거

사용자가 정답 없는 첨부 이미지의 유형 입력만 요청한 경우에는 내용·배치 검증을 별도 기록한다. 정답을 추정하거나 answer_matches를 true로 꾸며 전체 등록 완료 상태로 통과시키지 않는다. 원문과 다른 열 비율 등 남은 서식도 명시한다. 시험지·학년도·문항 번호가 사용자 자료와 충돌하면 출처 확인 전 확정 메타데이터를 재사용하지 않는다.

편집 담당은 저장 표시를 확인한 뒤 다른 문서로 이동했다가 같은 ID를 다시 열거나 새로고침한다. 재열람 시각과 문서 URL을 기록하고 원본 이미지·고정 초안 버전·저장된 본문을 함께 대조한다.

| 대상 | 대조할 내용 |
|---|---|
| 식별 | 시험·번호·유형·문서 ID·명세/초안 버전 |
| 발문/지문 | 시작과 끝, 문단/영역 읽기 순서, 배점, 누락·혼입 없음 |
| 수식 | 지수·분수·첨자·기호·조건, 올바른 렌더 및 편집 가능한 요소 |
| 답항/정답 | 원문 순서·개수·배열과 공식 정답표 일치 |
| 그림/박스 | 실제 이미지 로드, 축/주석 잘림 없음, 비율·정렬·헤더·간격 |
| 기타 | 표 구조, 대화체·옛한글·참조기호, 임시 내용 없음 |

해당하지 않는 요소는 해당 없음으로 구분하고 검사하지 않은 항목을 통과로 기록하지 않는다. 화면 증거는 문항 본문과 재열람 상태를 보여야 한다. 화면에 보이지 않는 정답 설정·긴 본문은 추가 화면 또는 허용된 읽기 전용 DOM/AX 관찰로 보완한다. 스크린샷 파일 경로만 존재하거나 체크값만 true인 것은 원본 정확성 증거가 아니다.

의미 오류는 마스터를 통해 추출 담당에게, 입력·배치 오류는 편집 담당에게 돌린다. 수정 후 영향을 받은 내용과 저장·재열람을 다시 확인한다.

## 마스터의 완료 심사

편집 담당의 검증 보고가 도착하면 마스터는 `submit`으로 토큰·사용 버전·증거·고정 입력 해시를 검사해 review_pending으로 접수한다. 이 상태에서는 편집 슬롯이 해제되어 다음 항목을 진행할 수 있다. 마스터가 실제 증거를 읽고 심사한 뒤 같은 토큰과 증거로 `finish`를 실행하며, CLI는 증거·스크린샷·원본·초안·자산 해시를 다시 검사한다. 심사 실패는 같은 편집 토큰으로 `return`하며 편집 중지 확인은 필요하지 않다. 총 요청 항목 수 = 유형별 합계 = 고유 대상 문서 수 = 검증 완료 수인지 실제 폴더와 기록을 대조한다. 지문은 문항 수와 따로 센다. 최대 번호만으로 누락 없음이라고 판단하지 않는다.

최종 보고에는 새 등록·기존 확인·보완 필요 개수, 문서 링크, 남은 항목을 명시한다. 과거 실행 증거나 모의 테스트를 이번 실제 등록으로 합산하지 않는다.

## 병렬 개선의 실행 검증

실제 마스터 1 + 추출 2 + 편집 1의 실행 핸들과 메시지, 항목별 추출 시작/끝·대기열 진입·편집 시작/끝·재열람 시간을 기록한다. 추출과 편집이 실제 겹쳐 실행됐는지 확인한다. 파일만 준비한 것은 병렬 실행 검증이 아니다.

사용자가 승인한 작은 범위에서 선택형·단답형·그림·박스·다중 영역 사례를 다룬다. 반환 경로와 중단 후 같은 ID 재개를 확인한 뒤 승인된 전체 범위를 수행한다. 오류 시험에 공식 문서를 손상시키지 않는다.

성능 비교는 동일 범위·유사 환경의 단일 실행과 비교하고 총시간, 추출/편집/대기시간, 오류 및 재작업 횟수를 보고한다. 조건이 다르거나 단일 실행 측정이 없으면 비교 미완료로 남기며 속도 향상률을 추정값으로 확정하지 않는다.

### 승인된 5문항 시험 실행

속도·모델 변경은 사용자가 승인한 연속 5문항 범위로 먼저 측정한다. 실행 전에 다섯 항목 ID, 문서 ID, 유형·복잡도, 원본·초안 버전과 비교 기준을 고정한다. 각 항목에 실제 마스터·추출·편집 agent ID, 사용 모델·추론 수준, assign·ready·claim·submit·finish 시각, 반환·재작업 횟수를 기록한다. `submit → 다음 claim`이 먼저 일어나고 이전 항목의 증거 심사가 겹쳤는지 이벤트와 메시지로 확인한다.

다섯 항목 모두 completed가 된 뒤 총 경과시간, 항목별 편집시간(claim→submit), 마스터 검수시간(submit→finish), 편집 슬롯 유휴시간, 오류·반환 수를 보고한다. 기존 비교 실행과 범위·환경이 같지 않으면 관찰값만 제시한다. 문서에 적힌 권장 모델은 적용 증거가 아니며 실제 spawn 인자와 핸들이 확인된 역할만 해당 모델로 측정한다. 일부 역할만 새 모델을 사용했으면 그 역할의 시험 결과로 구분하고 전체 권장 구성이 적용됐다고 보고하지 않는다.

현재 시험 실행의 편집 담당 `editor_astra`는 사용자의 명시적 변경에 따라 `gpt-6-astra`, `medium`, `fork_turns: "none"`으로 생성됐다. 이전 Luna low 담당의 두 제출은 스크린샷 심사에서 빈 발문 등의 문제로 반환됐으므로 완료 성능 표본으로 세지 않는다. 반환 원인에는 모델 외에도 편집 절차와 화면 확인이 영향을 줄 수 있으므로 두 제출만으로 속도·비용·정확도 우위를 결론 내리지 않는다.

## 검증 JSON

`submit`과 `finish`는 아래 증거를 받는다. version은 편집 배정의 version이며 screenshot은 작업 루트 기준 경로다. 사용한 토큰은 마스터에게 메시지로 보내고 CLI 인자로 전달한다. review_pending의 `finish`에는 `submit` 때 고정한 같은 증거 경로를 사용하며 파일이나 스크린샷이 바뀌면 거부된다.

```json
{
  "document_id": "실제 문서 ID", "version": 1,
  "saved": true, "reopened": true, "source_compared": true,
  "content_matches": true, "answer_matches": true,
  "screenshot": "verification/q01/reopened-v1.png",
  "reopened_at": "실제 재열람 시각", "document_url": "실제 편집 URL",
  "observations": "원본 및 초안과 대조한 실제 결과"
}
```

지문은 answer_matches가 필수는 아니다. 이 JSON의 true 값은 실제 검사 결과여야 한다. CLI는 파일 존재·ID/버전·해시·체크값을 검사하며 이미지가 보여주는 내용이나 실제 서버 저장을 판정하지 않는다. 마스터는 screenshot을 열고 보고된 문서/내용에 관한 증거인지 심사한 뒤 finish를 실행한다.
