# 마스터의 계획 및 빈 문서 준비

책임 경계는 [마스터 역할](roles/master.md), 도구로 에이전트를 실행하는 방법은 [실행 연결](orchestration.md)을 따른다.

## 실행 준비

새 요청의 추출 인원을 확인한다. 이미 개수가 지정됐으면 재질문하지 않는다. 학년도와 시행 연도를 구분하고 과목·선택과목·홀짝형·문항/지문 범위를 확정한다. 시험 식별을 바꾸는 모호함은 확인하되 검색과 기존 기록 조회는 먼저 진행한다.

작업 루트는 개발 프로젝트에서는 `runs/<run_id>/`, 설치판에서는 `connector.py status`의 runs 경로 아래 `<run_id>/`다. 실제 절대 경로 하나를 모든 담당자에게 전달한다. 실행 기록은 배포하지 않는다.

```text
<run_id>/
  manifest.json          마스터의 전체 목록·상태·ID·소유권
  source/                공식 문제·정답 PDF
  pages/                 페이지 이미지
  assignments/           문항별 영역·작업 명세
  extracted/<item_id>/    담당 추출자의 버전별 초안·그림
  queue/                 마스터의 ready·editing·review_pending·completed 기록
  verification/<item_id>/ 편집자의 재열람 증거
```

신규 기록을 만들기 전 `python scripts/parallel_run.py --help`와 사용할 하위 명령의 `--help`를 확인한다. CLI가 제공하는 초기화·검사·상태 전환을 이용한다. 문서의 구조 설명을 실제 JSON 필드명으로 추정하지 않는다. 기존 실행은 [레거시 재개 규칙](run-records.md)을 읽고 기존 ID를 재열람한다. 원기록을 변경하지 않고 필요한 매핑만 새 실행에 출처와 함께 기록한다.

## 원본과 항목 조사

1. 공식 게시물과 첨부의 학년도·과목·형을 확인한다. 문제·정답 PDF URL, 게시물 정보, 로컬 경로, SHA-256을 기록한다.
2. 등록 범위의 물리 페이지를 이미지화한다. PDF 전체에 다른 선택과목이 있으면 대상 페이지를 식별한 뒤 필요한 페이지만 렌더할 수 있다. 렌더 도구·배율/해상도·버전 및 각 이미지 크기를 기록한다.
3. 페이지를 직접 보며 항목의 시작·끝을 찾는다. 질문과 독립 지문 수를 따로 세고 선택형·단답형·일반 문서의 합계와 대조한다. 그림·수식·박스는 유형이 아니라 특성으로 기록한다.
4. 각 영역을 이미지 왼쪽 위 원점의 픽셀 `x, y, width, height`로 저장한다. 물리 페이지는 1부터, 인쇄 쪽은 별도 값으로 기록한다. 해당 이미지 경로·가로/세로 크기·렌더 버전을 반드시 함께 남긴다.
5. 여러 단/페이지에 걸치면 여러 영역과 읽기 순서를 기록한다. 관련 지문은 참조 ID로 연결하되 앱 내 연결은 만들지 않는다. 좌표는 이미지 경계 안에 있어야 하며 작은 주변 여백을 포함해 잘림 여부를 확인한다.
6. 문항 번호의 누락·중복, 총수·유형별 합계, 선택과목 중복 번호를 확인한다. 유형이 불확실하면 해당 항목의 빈 문서 생성·배정을 보류하고 판독한다.

## 빈 문서 생성과 인계

대상 폴더와 기존 ID를 실제 편집기에서 확인한다. 새 폴더 생성 시 첫 문서가 함께 생길 수 있으므로 그 문서도 수량에 포함한다. 유형별로 빈 문서를 만들고 생성 직후 문서 ID·URL·제목·최종 순서를 기록한다. 저장 결과가 불명확하면 목록과 기존 ID부터 확인한다.

전체 항목에 고유 ID와 올바른 유형이 연결됐는지 실제 폴더와 대조한다. 제목/최종 순서로 식별하고 준비 완료 순서가 원래 문항 순서를 바꾸지 않도록 한다. 브라우저 도구가 정렬을 지원하지 않으면 최종 순서의 확인 방법을 기록하고 정렬 완료라고 주장하지 않는다.

명세에는 작업/항목 ID, 유형·번호·순서, 대상 문서 ID, 원본 및 정답 출처, 이미지·좌표·읽기 순서, 관련 항목, 담당자·명세 버전을 제공한다. 배분 이후 원본은 읽기 전용이다. 원본/좌표를 바꾸면 버전을 갱신하고 이전 배정부터 회수한다.

마스터가 빈 문서 생성을 마친 뒤 편집기 탭 식별자와 제어권을 편집 담당에게 명시적으로 넘긴다. 이후 마스터는 그 탭을 조작하지 않는다. 구조 변경은 편집 담당의 중단 확인 후에만 제어권을 회수한다.

## 초기화 JSON과 상태 (schema_version 2)

`init <spec 파일>`은 다음 구조를 받는다. 예시 ID·좌표는 실제 실행 값으로 바꾼다. 먼저 `pages/`에 실제 이미지를 준비해야 `init`의 파일 존재 검사를 통과한다.

```json
{
  "exam": {
    "academic_year": 2025, "subject": "수학", "variant": "홀수형", "elective": "미적분",
    "source": {"question_pdf": "source/questions.pdf", "answer_pdf": "source/answers.pdf", "question_url": "공식 URL", "answer_url": "공식 URL", "question_sha256": "실제 해시", "answer_sha256": "실제 해시"},
    "render": {"tool": "사용한 도구", "version": "실제 버전", "scale": 1.7}
  },
  "extractors": 2,
  "items": [
    {"id": "q01", "type": "choice", "order": 1,
     "regions": [{"image": "pages/questions-1.png", "image_size": [1432, 2025], "bbox": [70, 160, 610, 330], "page": 1, "printed_page": "1"}],
     "related": []}
  ]
}
```

`type`은 `choice`, `short`, `passage` 중 하나다. 항목 ID와 order는 작업 내 유일해야 한다. regions 배열 순서가 읽기 순서이며 bbox는 `[x,y,width,height]`, image_size는 `[width,height]`다. 원본·렌더 부가 정보는 보존되는 `exam` 내부에 기록한다. 출처 URL/해시/이미지 실제 크기는 마스터가 확인한다. CLI 좌표 검사는 기록된 크기와 비교하므로 실제 이미지 크기 확인을 대체하지 않는다.

manifest의 items는 ID별 객체이며 `planned → empty → extracting → ready → editing → review_pending → completed`로 진행한다. 편집 담당이 검증 증거를 제출하면 `review_pending`에서 편집 슬롯이 해제되고, 마스터가 같은 증거와 원본·초안 해시를 다시 검사해 완료한다. 기존 실행 호환을 위해 `editing → completed`의 직접 완료도 지원한다. 보완 상태는 `needs_revision`이다. `assign`의 version은 추출 재배정마다 증가하며 `amend`의 spec_version은 명세 수정 때 증가한다(초기 기본 1). assignment_token과 edit_token은 별개다. `queue/`는 manifest에서 재생성되는 보기이므로 큐 파일을 직접 이동/수정하지 않는다.

제한된 시험 범위만 편집할 때는 `claim --only <id> [<id> ...]`를 사용한다. 지정 ID에 속한 ready 항목끼리 기존 ready_order의 FIFO를 유지하며, 범위 밖 ready 항목은 상태와 순서를 그대로 보존한다. 기본 `claim`은 전체 ready 대기열을 대상으로 한다.
