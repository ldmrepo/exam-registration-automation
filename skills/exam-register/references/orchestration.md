# Codex 병렬 실행 연결

이 문서는 실제 에이전트 호출과 파일/브라우저 소유권을 연결한다. Python 기록 도구는 에이전트 생성·브라우저 편집을 대신하지 않는다. 예약 작업이나 독립 무인 서비스를 설치하는 절차가 아니다.

## 시작 전

[내장 브라우저 운영](browser-policy.md)을 먼저 적용한다. 기본 브라우저는 iab이며, 전용 편집 담당이 접근할 수 없으면 마스터가 단일 편집 역할을 겸임한다. 아래 전용 편집 에이전트 생성·중계 절차는 전용 담당 모드에서 적용한다. 겸임 모드는 추출만 병렬이며 편집/최종 심사의 동시 수행을 주장하지 않는다.

마스터는 현재 사용자 요청을 수행하는 루트 에이전트다. 기본 추출 인원은 2명이지만 새 등록 요청에서 인원 답변을 받고 실행한다. 요청에 이미 지정됐다면 재질문하지 않는다. 마스터와 편집 담당을 포함한 실제 동시 실행 한도를 확인한다. 다른 작업이 슬롯을 쓰고 있다면 한도 안에서 조정하거나 사용자에게 가능한 구성을 설명한다.

`collaboration.spawn_agent`, `send_message`, `followup_task`, `list_agents`, `wait_agent`, `interrupt_agent`의 현재 도구 문서를 확인한다. 이 이름이 없는 환경에서 동일 명령이 있다고 가정하지 않는다. 도구가 제공되지 않으면 준비 자료를 완성하고 병렬 실행 불가를 명시한다.

기록의 명령/JSON 규격은 `python scripts/parallel_run.py --help`와 해당 하위 명령의 `--help`에서 확인한다. 상태 전환은 마스터가 이 도구로 수행한다. 추출/편집 담당에게 직접 manifest나 queue를 수정하게 하지 않는다. CLI가 증거 파일을 수락해도 마스터의 실제 원본 대조와 재열람 증거 심사를 생략하지 않는다.

## 실제 배분 순서

지원 환경에서는 마스터가 범위·최대 시간을 지정한 [인계 중계기](handoff-relay.md)를 실행해 아래 제출/다음 배정을 처리한다. 최종 시각 심사와 finish/return은 마스터가 직접 한다. 중계기를 사용할 수 없으면 아래 수동 submit-and-claim 인계를 사용한다. 코드의 실행 가능한 추출 인원은 현재1~2명이며 권장 인원을 늘리는 문서 변경만으로 확장되지 않는다.

1. [계획](planning.md)에 따라 원본·좌표·유형별 빈 문서·ID 매핑을 준비한다.
2. `collaboration.spawn_agent`로 `extractor_1`, `extractor_2`를 생성한다. 인원 선택에 따라 같은 역할 정의로 수를 조정한다. `message`에 아래 배정 템플릿을 실제 절대 경로와 ID로 채워 넣는다. `fork_turns: "none"`을 사용하고 전체 대화를 복제하지 않는다. 역할 지침, 항목 명세, 필요한 파일 경로와 현재 실행에 필요한 사실만 전달한다. 역할별 모델과 추론 수준은 아래 표의 실제 `model`·`reasoning_effort` spawn 인자로 지정한다.
3. `collaboration.spawn_agent`로 `editor`를 하나 생성한다. [편집 역할](roles/editor.md)과 [편집](editing.md)을 읽게 하고 편집기 제어권·브라우저/탭 ID를 전달한다. 마스터가 제어를 중지했음을 알리고 첫 편집 배정 전에는 준비 확인만 하게 한다. 편집 담당도 전체 대화 대신 역할·명세·필요 파일만 받는다.
4. 반환된 실제 agent ID를 역할·원본 열람 탭 또는 이미지 환경과 함께 기록한다. 마스터의 브라우저 핸들이 다른 에이전트에 자동 공유된다고 가정하지 않는다. 편집 담당은 현재 도구의 탭 선택 절차로 같은 대상 탭을 획득하고 읽기 관찰로 확인한다. 탭이 다른 에이전트 세션에 귀속돼 획득할 수 없으면 마스터가 기존 탭의 저장·조작 중지를 확인한 뒤 동일 문서 URL을 편집 담당의 새 탭에 열도록 인계한다. 새 문서를 생성하지 않는다. 추출 담당은 별도 원본 탭이나 파일 이미지 열람을 보고한다.
5. 추출 완료 메시지가 도착하면 산출물·버전·전체 페이지 대조·정답 근거·미해결 사항을 확인한다. 적격 결과만 공식 ready 상태로 접수한다. 에이전트 메시지 도착 순서보다 마스터가 인계를 승인한 순서를 기준으로 한다.
6. 편집 담당이 비어 있으면 가장 먼저 준비된 항목을 editing으로 배정하고 토큰을 발급한 후 `send_message`로 전달한다. 담당이 이미 종료/idle이면 `followup_task`로 재개한다. 작업 중인 에이전트의 다음 일을 메시지만으로 중복 실행시키지 않는다.
7. 편집 담당이 저장·재열람·원본 대조를 끝내고 증거를 제출하면 마스터는 `submit`으로 증거와 고정 입력의 해시를 검사해 `review_pending`으로 전환한다. 이때 단일 편집 슬롯이 해제되므로 다음 ready 항목을 즉시 배정할 수 있다. 마스터는 제출된 항목을 별도로 심사하고 같은 토큰·증거를 `finish`로 다시 검사해 완료하거나, `return`으로 보완 처리한다. `review_pending`은 편집기가 이미 해제된 상태이므로 반환할 때 `--editor-stopped`가 필요 없다.
8. 전체 항목 증거와 누락·중복을 확인한 후 에이전트에 종료를 알리고 최종 보고한다. 파일 작성·일부 등록만으로 전체 작업 완료로 처리하지 않는다.

## 역할별 모델과 추론 수준

| 역할 | 권장 모델·추론 | 적용 기준 |
|---|---|---|
| 마스터 | `gpt-5.6-sol`, `medium` | 배정, 상태 전환, 증거 심사와 최종 판단 |
| 추출·분석 | `gpt-5.6-terra`, `medium` | 원본 시각 판독, 수식·정답·영역 초안 작성 |
| 편집 | `gpt-6-astra`, `medium` | 브라우저 입력, 저장·재열람과 화면 증거 자체 점검 |
| 예외 해결 | `gpt-6-astra`, `high` | 반복 실패, 모호한 원본, 상태 충돌처럼 상위 판단이 필요한 경우에만 별도 배정 |

이 값은 권장 실행 구성이다. 실제 `spawn_agent` 호출에 모델과 추론 수준을 지정하고 반환된 핸들을 기록한 경우에만 적용됐다고 보고한다. 실행 중인 마스터의 모델은 문서를 바꿔도 자동 변경되지 않는다. 실측하지 않은 역할 조합의 속도·정확도 개선을 주장하지 않으며, 시험 실행에서 실제 사용한 역할·모델·추론 수준을 측정 기록에 구분한다.

속도 변경의 첫 검증은 [검증 절차의 승인된 5문항 시험 실행](verification.md#승인된-5문항-시험-실행)을 따른다. 다섯 문항 전체가 완료되기 전에는 부분 처리 시간을 전체 개선률로 환산하지 않는다.

현재 5문항 시험 실행에서는 사용자가 편집 모델을 Astra로 지정했고, `editor_astra`가 `gpt-6-astra`, `medium`, `fork_turns: "none"`으로 실제 생성됐다. 이는 이번 실행의 사용자 지정 설정이며 다른 역할의 권장값이나 기존 실행 기록을 소급해 바꾸지 않는다. 앞서 Luna low 편집 담당이 제출한 두 항목은 마스터의 스크린샷 심사에서 빈 발문 등의 문제로 반환됐다. 이 관찰만으로 어느 모델의 속도·비용·정확도 우위를 주장하지 않는다.

## 메시지 계약

아래는 도구 입력의 고정 JSON 스키마가 아니라 사람이 읽을 수 있는 필수 정보다. 경로·버전·토큰의 실제 값은 실행관리 도구의 결과를 사용한다. 비밀 키·로그인 인계 URL은 메시지와 기록에 넣지 않는다.

**추출 배정 메시지**

> 역할 정의 `<skill>/references/roles/extractor.md`와 extraction.md를 읽으세요. 작업 루트 `<absolute run path>`, 항목 `<id>`, 명세 `<assignment path>` 버전 `<version>`을 담당합니다. 원본 이미지와 정답표는 명세 경로에서 읽고 자신만의 원본 열람 환경을 사용하세요. `<run>/extracted/<id>/`만 작성하며 공식 기록·편집기는 수정하지 마세요. 결과는 새 버전으로 저장하고 원본 대조·미해결 사항과 함께 마스터에게 제출하세요.

**공통 회신**

| 메시지 | 필요한 내용 |
|---|---|
| READY | agent ID, 역할, 배정 항목, 독립 열람 환경/편집 탭 확인 |
| EXTRACTED | run/item ID, 명세·초안 버전, 산출물 경로, 원본 대조·정답 근거, 미해결 사항 |
| EDIT | run/item ID, 대상 문서 ID/URL, 명세·초안 버전, 고정 초안 경로, 배정 토큰 |
| EDITED | 문서 ID, 버전·토큰, 저장 관찰, 다음 재열람 단계 |
| VERIFIED | 문서 ID, 버전·토큰, 재열람·원본 대조 증거 경로, 미해결 없음 |
| NEEDS_REVISION | 항목·버전·토큰(있으면), 오류 종류, 원본/화면 위치, 현재 저장 상태, 요청 담당 |
| STOPPED | 중단한 항목·버전·토큰, 마지막 조작, 브라우저 제어 중지 확인 |

회신은 `collaboration.send_message`로 마스터에게 보낸다. 마스터는 모호하거나 오래된 버전의 회신을 완료로 받아들이지 않는다. 메시지 내용만 믿지 말고 지칭하는 로컬 산출물과 현재 배정 상태를 확인한다.

## 중단과 복구

저장 직후 편집 담당이 중단됐으나 초안에 수정이 필요하지 않으면 마스터는 `resume <id> <old edit_token> <observation JSON>`을 사용한다. 관찰 파일에는 `document_id`, `version`, `stopped: true`, `last_state`를 기록한다. 실제 담당 중지와 저장 상태 확인이 선행되어야 한다. 이 명령은 문서 ID와 초안 버전을 유지하고 편집 토큰만 교체한다. 편집 담당은 새 토큰을 받은 뒤 기존 문서를 열어 저장 내용을 확인하고 필요한 작업만 이어간다. 이전 토큰의 완료 보고는 거부한다. 원문/초안 수정이 필요한 경우에는 `return` 후 재추출 절차를 사용한다.

내장 브라우저가 서브에이전트에 없거나 `Browser is not available`이면 마스터 핸들 재사용을 반복하지 않는다. 외부 Chrome/Edge 전환 대신 [내장 브라우저 운영](browser-policy.md)의 마스터 편집 겸임 경로를 적용한다. 마스터도 접근할 수 없으면 준비·재개 기록을 보존하고 환경 문제를 보고한다.

`list_agents`로 실제 핸들 상태를 확인하고 `wait_agent`로 진행을 기다린다. 도구 관찰 타임아웃은 종료 증거가 아니다. 시간 경과나 오래된 queue 파일만으로 작업을 재배정하지 않는다.

편집 구조 변경·재배정이 필요하면 STOP 요청 후 STOPPED 회신과 제어 중지를 확인한다. 응답하지 않으면 `interrupt_agent`로 실제 중단을 확인하고 현재 문서 ID를 읽기 재열람해 저장 상태를 기록한다. 마스터가 토큰을 취소/갱신한 뒤에만 새 배정한다. 새 토큰으로 넘어간 뒤 도착한 이전 토큰의 결과는 반영하지 않는다.

브라우저 또는 인증 장애 시 [레거시 재개 규칙](run-records.md)의 기존 ID 우선 확인 원칙을 유지한다. 실제 문서 내용이 초안과 다른 경우 사용자 수정인지 확인하며 자동 덮어쓰지 않는다. 결과 제출 전에 에이전트가 종료돼도 완료 파일만으로 검증 완료를 추정하지 않는다. 저장·재열람을 다시 확인하고 기존 ID를 유지한다.

원본/좌표 수정은 마스터가 새 명세 버전을 발행하고 담당자에게 재배분한다. 초안 보완은 추출자가 새 버전을 작성한다. 편집 중인 버전은 덮어쓰지 않으며 중단 확인 전에는 대기열 교체를 진행하지 않는다.

## 실행관리 CLI 호출 순서

모든 명령은 마스터만 실행한다. 공통 접두사는 `python scripts/parallel_run.py --run <절대 작업 경로>`다. 각 명령의 최신 인자는 `--help`로 확인한다.

| 명령 | 실제 효과 |
|---|---|
| `init <spec 파일>` | v2 manifest 초기화. 기존 manifest가 있으면 거부 |
| `bind <id> <document_id>` | UI에서 실제 생성/확인한 빈 문서 ID 연결 |
| `remap <id> <observation 상대경로>` | 작업 반환 후 실제 확인한 문서 ID·유형으로 매핑 보완, 명세 버전 증가 |
| `assign <id> extractor-1` | 모든 문서 연결 후 추출 배정·version·assignment_token 생성 |
| `ready <id> <assignment_token> <draft 상대경로>` | 마스터가 심사한 초안의 파일/영역/버전 검사 및 ready 접수 |
| `claim` | 가장 먼저 승인된 ready 하나를 editing으로 전환, edit_token 반환 |
| `claim --only <id> [<id> ...]` | 지정 범위의 ready 중 가장 먼저 승인된 하나만 editing으로 전환. 다른 ready는 유지하며 중복·미등록 ID는 거부 |
| `submit <id> <edit_token> <evidence 상대경로>` | 편집 담당 증거와 원본·초안·자산 해시를 검사해 review_pending으로 전환하고 편집 슬롯 해제 |
| `submit-and-claim <id> <edit_token> <evidence 상대경로> --only <id> [<id> ...]` | 단일 manifest 트랜잭션으로 submit 후 범위 내 FIFO claim. `{submitted, next}` 반환. next가 없으면 null이며 접수는 성공 |
| `preview-next --only <id> [<id> ...]` | 다음 ready의 고정 경로·ID·버전·해시를 읽기 전용 조회. 토큰과 소유권을 발급하지 않으며 preview_only=true 반환 |
| `finish <id> <edit_token> <evidence 상대경로>` | editing(기존 호환) 또는 review_pending의 재열람 증거와 해시를 다시 검사한 후 completed 기록 |
| `return <id> <현재 토큰> <사유>` | 추출/ready 작업을 needs_revision으로 반환 |
| `return <id> <edit_token> <사유> --editor-stopped` | 실제 편집 중지와 저장 상태 확인 후 편집 작업 반환 |
| `return <id> <edit_token> <사유>` | review_pending 심사 실패를 needs_revision으로 반환. 편집 슬롯은 이미 해제되어 중지 확인 불필요 |
| `amend <id> <patch 상대경로>` | empty/needs_revision 항목의 regions·related 보완(reason 필수) |
| `status` | 현재 manifest 조회 |
| `rebuild` | 마스터 잠금 안에서 manifest 기준 대기열 재생성. 기존 문항 상태·ID·토큰 유지 |

spawn의 task_name은 `extractor_1`처럼 만들고 CLI owner는 `extractor-1`로 기록한다. 마스터가 실제 agent ID와 이 owner의 대응을 유지한다. 다른 추출 담당도 동일하게 배정한다.

## 접수와 다음 배정을 한 번에 수행하기

VERIFIED는 증거 파일 작성과 재열람 대조가 끝나면 긴 설명을 기다리지 말고 항목·문서 ID, 버전·토큰, 증거 경로, 미해결 없음과 조작 중지를 짧게 즉시 전송한다. 마스터는 접수 결과의 next를 긴 보고서로 다시 작성하지 않고 run 경로·ID·문서 ID/URL·명세/초안 버전·초안 경로·edit_token을 담은 짧은 EDIT로 즉시 배정한다. 이전 항목의 시각 심사는 그 뒤 새 항목 편집과 병행한다. 공식 상태 변경은 계속 마스터만 담당한다.

실제 배분 순서 7단계에서 다음 항목을 바로 이어갈 때는 별도 submit/claim 대신 `submit-and-claim`을 사용한다. 편집 담당이 저장·재열람·원본 대조를 끝내고 브라우저 조작을 멈춘 VERIFIED를 제출한 뒤 마스터가 호출한다. 반환된 `next`의 경로·ID·버전·새 토큰으로 EDIT를 즉시 전달하고 이전 항목의 스크린샷 심사를 이어간다. 접수는 마스터의 시각 심사 통과를 뜻하지 않는다. 같은 토큰·증거로 finish 또는 return을 처리한다.

`submit-and-claim`과 `preview-next`에서 `--only`를 생략하면 전체 run 범위다. 부분 승인 실행에서는 항상 승인된 ID를 명시한다. 인자 중복·미등록 ID, 현재 증거 또는 다음 항목의 고정 입력 검증 실패는 트랜잭션 전체를 취소하며 현재 항목은 editing에 남는다. 다음 ready가 없으면 접수는 성공하고 `next: null`이다. `next`는 기존 claim 형식의 항목에 명세 버전(기본 1)을 포함한다. 초안과 원본 경로는 run 기준 상대 경로다.

편집 중 `preview-next`로 다음 초안·원본의 로컬 파일을 미리 읽을 수 있다. 조회는 revision·이벤트·대기열을 변경하지 않으며 실제 배정 전에 결과가 달라질 수 있다. preview에는 토큰·owner가 없고 브라우저 이동·편집 권한도 없다. 편집 담당은 실제 EDIT의 ID·버전·해시와 일치할 때만 미리 읽은 내용을 사용한다. 새 문항으로의 브라우저 이동은 이전 문항 검증 제출과 새 토큰 인계 후 수행한다.

submit-and-claim이 파일 접근 오류로 끝나면 manifest에 두 전환이 이미 커밋됐을 수 있다. 명령을 반복하지 말고 status로 현재 review_pending과 editing 토큰을 확인한다. 투영 오류는 rebuild로 복구하고 기존 토큰을 인계한다. 이 경우 새 배정이나 resume으로 토큰을 임의 갱신하지 않는다.

`amend`는 문서 유형·ID 변경용이 아니다. patch에는 regions/related/reason만 넣는다. 유형/문서 ID 오류는 현재 작업을 중단·반환하고 실제 문서와 전체 매핑을 확인한 다음 `remap`을 사용한다. 관찰 JSON에는 previous_document_id/document_id/type/target_verified/reason을 기록한다. target_verified는 브라우저에서 해당 ID와 유형을 확인한 후에만 true로 기록한다. remap은 외부 문서를 생성·삭제·수정하지 않으며 이전 매핑을 이벤트에 남긴다. 이후 assign으로 새 버전·토큰을 발급하고 수정된 대상으로 새 초안을 작성한다. 기존 문서 보존이나 정리 여부는 별도로 관리한다. 현재 CLI가 추출 인원을 1 또는 2로 제한하므로 그 이상을 지원하려면 실행 한도 확인과 함께 코드·검증도 갱신해야 한다.

manifest가 진실 원본이고 queue는 재생성 가능한 투영이다. `.coordinator.lock`이 있으면 기록된 소유 프로세스가 실제 종료됐는지 확인한다. 오래됐다는 이유만으로 잠금을 제거하지 않는다. 잠금만으로 에이전트 생존/사망을 판단하지 않고 실제 협업 핸들과 브라우저 상태도 확인한다.

명령이 파일 접근 오류로 끝나도 manifest 쓰기가 먼저 성공했을 수 있다. 같은 assign/claim을 반복하지 말고 `status`로 기존 배정과 토큰을 확인한다. 대기열 투영만 실패했다면 `rebuild`로 복구하고, 아직 전달하지 않은 기존 토큰을 해당 담당자에게 인계한다. 파일 교체는 일시적인 PermissionError를 최대 4회 시도하며 지속 실패는 숨기지 않는다. `rebuild`는 편집 소유권을 갱신하지 않으므로 실제 담당자 중단 시 사용하는 `resume`과 구분한다.
